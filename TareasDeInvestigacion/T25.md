# T025 — Anonimización genérica dentro de MP-SPDZ

## Alcance y componentes

Se reutiliza el [contrato T024](T24.md), sin cambios en sus modelos. El cliente
prepara las regiones de cada cuadro y una máscara pública por bloque. Los píxeles
originales continúan entrando por ExternalIO como valores secretos. El programa
`mpc/Programs/Source/delta_video_anonymize.mpc` los modifica dentro de MP-SPDZ:
`salida = píxel_secreto * (1 - máscara_pública)`.

La máscara vale 1 dentro de cualquier rectángulo y 0 fuera. Rostros y placas usan
el mismo cálculo; las superposiciones se unen. Solo se revela la salida procesada
al cliente, no una salida original seguida de ocultamiento local. Se conserva
replicated-ring de 64 bits, tres parties, 20 segundos, 10 FPS, máximo 640×480,
gris, proporción y ausencia de ampliación de videos pequeños.

## Interfaz para T021/T023

```python
from client.anonymization import prepare_anonymization

plan = prepare_anonymization(
    frames,  # FrameDetections de TODOS los cuadros procesados, incluidos vacíos.
    source_size=(original_width, original_height),
    target_size=(processed.metadata.width, processed.metadata.height),
    frame_count=processed.metadata.frame_count,
)
result = mpc_client.process_anonymize(processed.payload, plan)
```

Para ejecutar el ciclo HTTP y reconstrucción existente, llamar `upload_video`
con `processing_mode="anonymize"` y `anonymization_plan=plan`. Las dimensiones y
cantidad deben coincidir exactamente con el preprocesamiento realizado. T021 y
T023 conectarán sus adaptadores a esta interfaz; no se implementan aquí ni T022.

La preparación completa ocurre **antes** de registrar el job o enviar píxeles.
Un detector fallido o un cuadro faltante producen error, nunca éxito vacío ni
fallback. `plan.validate_result(original, result)` comprueba dentro=0 y fuera
sin cambios; es validación, no ocultamiento en el cliente.
El constructor directo `AnonymizationPlan(...)` solo valida geometría y sirve
para diagnóstico local: no habilita transporte. La CLI y ExternalIO exigen la
marca interna de preparación completa que establece `prepare_anonymization`;
declarar cajas o una lista vacía no reemplaza los resultados de cada detector.

## Protocolo público y privado

1. Identidad explícita: cabecera pública `[longitud positiva, cantidad de bloques]`,
   compatible con el transporte anterior. `delta_video_identity.mpc` se conserva.
2. Anonimización: cabecera `[-longitud, cantidad de bloques]`. Cada party debe
   confirmar el ACK público `[1145852993, 1]` antes de transmitir píxeles privados.
   La espera de ese ACK es acotada; un programa incompatible produce error.
3. Por bloque: máscara pública de 4096 enteros 0/1, 4096 píxeles privados,
   procesamiento vectorizado en MPC y resultado exclusivo al cliente.
4. El último bloque usa padding cero. El orden lineal es cuadro/fila/columna;
   la máscara respeta ese orden incluso cuando el bloque cruza entre cuadros.

El MPC valida la longitud, cantidad de bloques y máscara binaria. No hay
comparaciones secretas de coordenadas, cambios a Secret Sharing ni despliegue
de redes neuronales. El programa usa bucles públicos y vectores; no se expande
el código para cada píxel o resolución. Los paquetes lógicos de 10 cuadros de
T024 no afectan estos bloques.
Un proxy de sockets detecta EOF y lecturas incompletas durante el intercambio,
sin modificar el cliente criptográfico upstream. Una conexión cortada no se
interpreta como éxito ni puede dejar al lector girando indefinidamente en EOF.

Son públicos la longitud y posiciones a ocultar: la máscara revela información
del contenido. Los valores originales de los píxeles permanecen secretos. El
tipo face/plate se conserva en T024, pero no necesita transmitirse al circuito.

## CLI de diagnóstico

```powershell
$env:MPC_PROGRAM="delta_video_anonymize"
docker compose up --build -d
python -m client upload video.mp4 --processing-mode anonymize --regions-json regiones.json
```

El JSON es una entrada opcional de prueba/manual, no el transporte a MPC. Sus
coordenadas ya corresponden a la resolución MPC. Debe tener las dimensiones
reales y un resultado por cada cuadro procesado:

```json
{
  "width": 64,
  "height": 48,
  "frames": [
    {"frame_index": 0, "status": "success", "regions": [
      {"region_type": "face", "x": 10, "y": 8, "width": 20, "height": 12}
    ]},
    {"frame_index": 1, "status": "success", "regions": []}
  ]
}
```

Un fallo se declara `{"frame_index": 1, "status": "failed", "error": "detalle"}`.
No se deduce éxito de un registro incompleto. La CLI sin selección conserva
identidad y muestra que no anonimiza; no usa silenciosamente las detecciones
YuNet ni sustituye las integraciones pendientes con un CSV.

## Verificación y límites

Las pruebas comparan arrays antes de codificar MP4, porque el codec puede cambiar
valores al decodificar. También se comprueban dimensiones, FPS y archivo válido.
La validación final ejecutó la suite completa: **407 tests pasaron**, incluidos
los tres E2E reales; cinco avisos de dependencias/upstream no bloqueantes.
Pasaron el E2E anterior de identidad y dos E2E de anonimización usando las tres
parties reales del Compose habitual. Las entradas privadas originales y máscaras
públicas se observaron mediante el cliente oficial; un oracle NumPy independiente
se usó solamente en tests para comparar ceros interiores e igualdad exterior.

| Resolución MPC | Video probado | Tiempo MPC | Flujo completo |
|---|---|---:|---:|
| 64×48 | 2 s, 4 cuadros a 2 FPS | 0,700 s | 7,443 s |
| 128×96 (original 256×192) | 2 s, 4 cuadros a 2 FPS | 2,318 s | 8,916 s |
| 640×480 | 1 s, 10 cuadros a 10 FPS | 137,610 s | 145,093 s |

Los dos primeros se repitieron tras las validaciones finales de preparación y
EOF. El tercero fue una medición adicional previa a esas guardas; utiliza el
mismo circuito y máscaras, no demuestra tiempo real. El programa compilado tiene
272 instrucciones; las capas pesadas de Docker utilizaron caché. Evidencia local
en `.runtime/T025/summary.json` y `e2e-final-results.xml`.

El límite de entrada no demuestra viabilidad de 20 segundos a 640×480/10 FPS,
ni ejecución en Raspberry Pi. El modelo de privacidad continúa siendo el MVP
semi-honesto con certificados de desarrollo y las parties en una computadora.
