# T49 — Implementación del cliente web

Fecha de implementación: 16 de noviembre de 2026 (America/Costa_Rica).
Base: `bcebf198c53db39e91e5ba0ea54f639d67529c58`, repositorio inicialmente limpio.
El requerimiento y el plan aprobado se conservan en `../T49.md`.

## Recorrido implementado

La selección inicia automáticamente un worker. El archivo `File` se copia al
worker mediante structured clone local, no mediante HTTP. MP4Box obtiene la pista,
los cuadros y el FPS real. El navegador solicita un turno FIFO enviando únicamente
nombre/formato. Mientras espera conserva el original en su equipo.

Con turno, carga los tres ONNX y sus runtimes desde el mismo servidor web. YuNet
usa BGR nativo con padding negro a múltiplos de 32, confianza estrictamente mayor
que 0,6, NMS 0,3/topK 5000; LPD usa BGR nativo, las mismas anclas y esquinas,
confianza 0,6, NMS 0,3/topK 5000/keepTopK 750. YOLOX-S conserva RGB 0..255,
letterbox superior/izquierdo 640×640 con relleno 114, clases 0/2, umbral 0,4 y
NMS 0,45. El seguimiento conserva asociación por clase/IoU/movimiento, tres hits
y TTL de 60 cuadros ausentes. No se reinicia entre bloques. YOLO no crea máscaras.

`frontend/scripts/prepare-assets.cjs` publica los mismos modelos locales y sus
licencias. YuNet/LPD declaran tamaños fijos en ONNX aunque OpenCV acepta tamaño
nativo: el script cambia solamente las declaraciones espaciales y descarta pistas
de shape obsoletas. Comprueba que cada initializer conserve exactamente sus
bytes. No modifica pesos, operadores ni umbrales. El manifiesto registra hashes
fuente y derivados; el navegador comprueba los derivados al cargar.

WebCodecs decodifica H.264. Si el códec no está soportado, FFmpeg/WASM decodifica
localmente en grupos de ocho cuadros. Se usa para `video3.mp4` (MPEG-4 Part 2,
FOURCC FMP4; no significa aquí MP4 fragmentado). El fallback vuelve a decodificar
desde el inicio para seleccionar cada grupo: prioriza orden exacto sobre velocidad.
No hay transcodificación del original en un servidor.

Se conserva el muestreo por índice/FPS, hasta 30 FPS, la proporción, la caja
1920×1080, dimensiones pares y gris uint8. Cada cuadro debe terminar sus tres
inferencias antes de que sus píxeles se añadan al bloque privado. Un error de
inferencia aborta el trabajo. Las máscaras unen rostros y placas, se recortan y
redondean hacia afuera, con bordes finales exclusivos.

## ExternalIO y frontera de confianza

El navegador abre tres WebSockets directamente a los tres Node Agents. El
adaptador de cada party solo puede abrir TCP a `127.0.0.1:14000+party_id` dentro de
su propio contenedor. Presenta C0 y verifica el certificado TLS P0/P1/P2. Un
mensaje WebSocket equivale al cuerpo de un octetStream; el adaptador añade o
retira únicamente la longitud little-endian del transporte TCP.

La especificación debe coincidir en las tres conexiones y declarar Z2(64) tanto
para dominio secreto como claro. El header negativo selecciona anonimización;
las tres confirmaciones `[1145852993,1]` preceden cualquier entrada privada.
El bloque sigue siendo 262144 y el último se rellena con ceros. Las contribuciones
aleatorias se suman exclusivamente en el navegador; el navegador les añade sus
píxeles y envía el mensaje enmascarado a cada party. Ningún adaptador reúne las
contribuciones de los otros dos.

La implementación exacta usa dos palabras uint32: los intermedios de la suma de
tres palabras y su carry son menores que 2^34, representables exactamente como
Number. No convierte un entero completo de 64 bits a Number. Header y ACK usan
BigInt/DataView. Las pruebas cubren carries, wraparound y valores mayores que
2^53. No se usa XOR ni se rediseñó el protocolo semi-honesto.

El circuito fuente permanece sin cambios. Continúa calculando dentro de MP-SPDZ
`salida = secreto × (1 − máscara pública)`. El cliente comprueba cada palabra de
salida, incluidos bits altos y padding: cero dentro de la máscara e igualdad
exacta fuera. Solo después entrega los cuadros a un codificador. No sustituye la
anonimización MPC por una operación local ni tiene fallback a identidad.

Las llaves se separan en `.runtime/party-N/Player-Data/`: cada party monta su
llave Pn, la llave C0 y certificados públicos, sin las llaves privadas Pm de las
otras parties. La raíz de certificados completa queda disponible para la CLI de
diagnóstico en el host. El operador del host Docker sigue controlando todos los
servicios; no se ofrece protección frente a su colusión ni frente a código web
malicioso servido al usuario. Se conserva el modelo de seguridad aprobado.

## Cola e interrupciones

`POST /api/v1/browser-jobs` recibe JSON nominal y devuelve ticket/posición.
Estados: `QUEUED → READY → PROCESSING → STORING → COMPLETED`, o `FAILED`.
`GET /{ticket}` devuelve estado y renueva la lease. El worker envía heartbeat cada
10 s; el Coordinator revisa expiraciones cada 5 s, con plazo predeterminado de
90 s (`DELTA_LEASE_SECONDS`). `DELETE /{ticket}` aborta. El cierre usa keepalive
cuando es posible; una terminación abrupta depende del timeout y del cleanup,
sin prometer liberación instantánea.

El Coordinator prepara e inicia los tres Node Agents mediante sus URLs internas.
No recibe tensores, imágenes ni mensajes de ExternalIO. Primero limpia todas las
parties y solo entonces concede el siguiente turno. Si falla un cleanup, conserva
el turno y reintenta para evitar solapar runtimes. Las leases y el historial viven
en memoria; usar un único proceso Uvicorn. No hay recuperación tras reinicio.

## Resultado y contrato de almacenamiento v1

VideoEncoder H.264/MP4 es la primera opción de salida. FFmpeg/WASM mantiene una
alternativa local de codificación/concatenación. El resultado es gris, sin audio,
con el orden de cuadros y FPS de muestreo. La comparación exacta ocurre antes del
códec: la compresión posterior introduce pérdidas.

| Operación | Contrato |
| --- | --- |
| `POST /api/v1/results` | Multipart `video` (`video/mp4`) y `counts` (JSON); 201 con id, tamaño, SHA-256 y URL de descarga. Persiste un resultado aún no publicado. |
| `POST /api/v1/results/{id}/publish` | Publica idempotentemente el resultado después de completar/limpiar MPC. Devuelve el registro. |
| `GET /api/v1/results` | Lista solo resultados publicados con archivo existente. |
| `GET /api/v1/results/{id}/download` | MP4 adjunto; 404 si falta o aún no fue publicado. |
| `GET /health` | Salud del servicio. |

Campos de un registro: `id`, `filename`, `size`, `sha256`, `counts`, `created_at`,
`published`, `download_url` relativa al servicio. Los nombres de disco son UUID;
el nombre de subida no se usa como ruta. SQLite es catálogo, no almacén BLOB.
El archivo se escribe `.partial`, se sincroniza y renombra antes de insertar el
registro. La subida interrumpida se limpia y no aparece en el listado. El paso de
publicación evita mostrar resultados si falla la finalización de MPC. No hay
retención/borrado automático de resultados pendientes o publicados en este MVP.

El servicio confía en la validación del navegador. Comprueba formato básico y
escritura completa, pero no puede demostrar por sí mismo que una subida arbitraria
provenga de MPC. Las APIs y el catálogo son demostrativos, sin autenticación.

Ambas webs leen `DELTA_STORAGE_URL` desde `/config.js`, generado con jq al iniciar
el contenedor. Para reemplazar el servidor basta cambiar la URL si implementa
este contrato completo, incluida la publicación. No se conecta a cualquier BD
arbitraria cambiando su dirección. URLs internas del Coordinator/parties y URLs
públicas para el navegador se configuran por separado.

## Limpieza y operación

Se retiraron `client.local_api`, su servicio Compose, el cliente HTTP de subida,
sus pruebas y el E2E que validaba la arquitectura anterior. Se retiraron también
el generador XOR, API/servicio de shares y almacenamiento T09 no montados. No se
borraron artefactos históricos del usuario. La CLI, modelos Python, geometría y
ExternalIO Python permanecen como herramientas de diagnóstico y referencia.

`docker/web.Dockerfile` compila ambas webs y las sirve con nginx, MIME correcto
para `.mjs`/WASM y COOP/COEP. `docker/mp-spdz.Dockerfile` compila el runtime desde
el clon hermano. `docker/mpc-overlay.Dockerfile` permite reutilizar un binario
MP-SPDZ ya compilado, pero siempre recompila el circuito vigente: la imagen TAR
histórica contenía bloques de 4096 y fue rechazada antes de enviar píxeles.

Para esta validación se cargó la imagen TAR existente y se construyó el overlay
`proyecto-delta-mpc-party:t49`, sin modificar el clon hermano ni los originales.
El build habitual desde el código fuente sigue disponible. No se publicó un
sitio, no se hizo commit y no se desplegó al clúster del TEC.

## Validación y límites observados

Las evidencias locales se guardan en `.runtime/t49-evidence/`. Las pruebas de
aceptación recorren ambos frontends y Docker/MP-SPDZ reales. `t49-real.spec.ts`
registra únicamente metadatos HTTP y resultados; desactiva el trazado binario de
WebSockets para evitar que el propio sistema de trazas distorsione la medición.
La única solicitud multipart permitida es el resultado dirigido a almacenamiento;
los POST de control son JSON pequeños y no se contacta al antiguo puerto 8001.

Se comprobaron los tres códecs/modelos en Chrome. La paridad con OpenCV usa los
mismos seis PNG locales (cuadros 0 y 45 de cada original), sin diferencias de
decodificador. En esa muestra coinciden clases/cantidades: rostros y placas tienen
delta máximo de caja 0,000031 píxeles y confianza 0,0000003; YOLO tiene delta
máximo 0,947 píxeles y confianza 0,023512. Son diferencias reales de ejecución y
redondeo de resize, no una prueba de identidad numérica universal o de precisión.

El POST multipart puede no exponer su cuerpo mediante Playwright; una longitud
ausente en el registro no significa que la subida esté vacía. Los tamaños de los
resultados se comprueban de forma independiente en catálogo y descarga.

La persistencia se verificó reiniciando el contenedor de almacenamiento y
descargando desde la segunda web: 1515308 bytes, SHA-256
`50b0393754dbf78b5c86228b120b26d41ae7977f5e90c57b124ab3ccf33b3149`.
Pasaron 557 pruebas Python (siete E2E Python excluidos), 73 pruebas frontend, siete
regresiones de interfaz, paridad sobre seis cuadros, codificación fraccionaria y
la prueba real de tres bloques/padding: 524304 píxeles verificados, tres máscaras,
tres entradas enmascaradas y seis contribuciones por canal. La regresión anterior
tenía 23 pruebas adicionales del prototipo T09 retirado.

`video1.mp4` completó 596 cuadros en 1110,383 s incluyendo la espera inicial:
673,486 s de inferencia y 338,957 s de intercambio MPC. `video3.mp4` completó
90 cuadros en 326,223 s: 140,374 s de inferencia y 170,277 s de intercambio.
Los dos se descargaron desde el catálogo. La prueba completa de `video2.mp4`
se interrumpió para entregar el equipo al usuario, que continuará las pruebas;
no tiene resultado final verificado. Su primera ejecución detectó que el muxer solo acepta `frameRate` entero. Se
retiró ese argumento opcional y se conserva la frecuencia mediante timestamps
explícitos; una prueba con 60 cuadros a 29,6713995943 FPS comprobó duración y FPS.

El código del MVP está implementado; la aceptación completa de los tres videos
queda pendiente por `video2.mp4`. Se canceló únicamente el turno de esa prueba
(`8e7ef6e9-b257-47f8-94f8-a77cc889fdec`) y se liberaron las parties. La segunda
ejecución había superado 825 de 2438 cuadros; no se presenta como prueba aprobada.
`docs/T49-validation.json` reúne evidencia de los dos videos terminados y marca
explícitamente el pendiente. Se genera con `python scripts/t49_report.py --available`.
El usuario puede probar en `http://localhost:8080` y descargar en
`http://localhost:8081`. Para repetir solo el E2E pendiente, desde `frontend/`,
usar los comandos del README añadiendo `$env:T49_VIDEO="video2.mp4"`.

Equipo observado: Windows, Docker Desktop, Intel i5-1135G7 (4 núcleos/8 hilos),
7,65 GiB de RAM y Chrome for Testing 157.0.8103.78. Playwright utiliza un user-agent
de compatibilidad Chrome 156, que no identifica la versión real del binario.
Una muestra de memoria de Chrome sumó 279891968 bytes (~267 MiB); no es un pico
garantizado ni un requisito mínimo de RAM. Las mediciones incluyen actividad de
desarrollo/pruebas y no constituyen un benchmark aislado.

El coste de comunicación se conserva: por bloque, cada una de las tres conexiones
transporta máscara pública, contribución aleatoria, entrada enmascarada y
contribución de salida, todas de 64 bits. Son `96 × 262144` bytes de cuerpos por
bloque, más especificación/header/ACK. El informe calcula ese volumen antes de
compresión de transporte; no lo presenta como captura de tráfico físico ni
incluye TLS, framing o comunicación entre parties. Trasladar el cliente al
navegador no elimina esta expansión respecto al MP4 comprimido.

El navegador retiene el MP4 comprimido y la salida comprimida en memoria. Los
cuadros, tensores y buffers MPC se procesan/liberan por tramos, sin acumular todos
los píxeles del video. FFmpeg/WASM usa memoria de 32 bits y copias adicionales.
No se garantizan duración/tamaño ilimitados, 30 minutos/30 GB ni tiempo real.

La web usa el perfil predeterminado 1920×1080/30; conservar los límites de
aceptación de los servicios compatibles con ese perfil. La CLI mantiene sus
opciones de perfil. La lista de códecs no es universal. Brave instalado en este
equipo falló al arrancar por un error de inicialización de `chrome.dll`; no se
declara compatibilidad verificada en Brave. Los modelos pueden omitir rostros o
placas y los conteos pueden duplicar trayectorias tras reingresos. No se midió una
capacidad máxima de memoria ni se demostró aislamiento entre operadores remotos.
